qh docs

qh is a coding agent in your terminal. It reads and edits your files, runs commands, browses the web, and runs several agents side by side. It works with free local models, with your ChatGPT plan, or with an API key, and you can work on a project together with friends.

InstallOne command on Windows, Linux or Mac. Connect a modelLocal, Ollama cloud, ChatGPT or an API key. Use itAsk in plain words; qh asks before it changes things. Work as a teamSee who's online and what their agents are doing.

Install

Windows

Open PowerShell and run:

irm kesavsabari.github.io/qh | iex

Linux and macOS

curl -fsSL kesavsabari.github.io/qh/sh | sh

Then open a new terminal, so qh is on your PATH.

Updating

qh looks for a new version once a day. When there is one, the bottom line says Update available! Run: qh update. Run it in a terminal, or type /update inside qh, then restart qh.

qh update
qh --version

qh only installs a release signed with the qh release key, checks the download against it, makes sure it starts, and never installs an older version. The daily check fetches two small files from GitHub and sends nothing about you; turn it off with update_check = "off" in config.toml. qh 0.1.3 and older can't update themselves: run the install command above once more.

On Windows, qh runs commands with Git Bash if it's installed, otherwise PowerShell. Installing Git also gives you git, which team mode needs.

First run

Go to a project folder and type qh. The first time, a setup screen asks which models you want. Move with ↑ ↓, tick with Space, continue with Enter. You can tick several.

Run qh setup any time to change this.

Using qh

Type what you want in plain words and press Enter:

fix the failing test in tests/test_api.py
add a --verbose flag to main.py
what does src/engine.rs do?

The agent reads files, runs commands and edits code to do it. Before it changes anything it asks you, showing exactly what it will do (see modes).

  • Attach a file to your message with @path/to/file.
  • Stop the agent at any moment with Esc.
  • Type / to see every command; keep typing to narrow the list, Enter runs the highlighted one.
  • Run one task without the full screen: qh -p "explain this repo" -y.

Headless and CI

qh -p "…" --json prints one JSON object per line (JSONL) instead of plain text:

{"type":"start","model":"…","mode":"auto","version":"…","prompts":1,"max_turns":30}
{"type":"text","delta":"Running the tests…"}
{"type":"tool_call","name":"bash","args":{"cmd":"cargo test"}}
{"type":"tool_result","name":"bash","ok":true,"summary":"…"}
{"type":"diff","path":"src/lib.rs","added":3,"removed":1}
{"type":"permission_denied","tool":"…","message":"…"}
{"type":"usage","input":12000,"cached":8000,"output":900,"cost":0.004,"plan":false}
{"type":"error","message":"…"}
{"type":"done","ok":true,"code":0,"answer":"…"}

--mode ask|auto-edit|auto|plan works with -p. Anything that would need a prompt is refused, since nobody can answer, and reported as permission_denied. --max-turns N stops a prompt after N tool rounds.

Exit codes: 0 success, 1 agent error (or --max-turns hit), 2 bad usage, 3 a permission was needed and refused.

Example GitHub Actions workflow that lets qh fix failing tests on a pull request (the key comes from a repository secret, passed as an env var):

name: qh fix tests
on:
  pull_request:
jobs:
  fix:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.head_ref }}
      - run: curl -fsSL kesavsabari.github.io/qh/sh | sh
      - name: Let qh fix failing tests
        env:
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
        run: |
          qh -p "Run the test suite, fix whatever fails, and rerun until it passes." \
             --model openrouter:qwen/qwen3-coder --mode auto --max-turns 30 --json > qh.jsonl
      - name: Commit the fix
        run: |
          git config user.name qh-bot
          git config user.email qh-bot@users.noreply.github.com
          git commit -am "qh: fix failing tests" && git push || true

Local models (Ollama)

Install Ollama (Windows: winget install Ollama.Ollama), start it, and run qh setup. Setup offers to download qwen3.5:9b, the model qh is tuned on. Any other Ollama model works too: ollama pull <name> and it shows up in /model.

qh sizes the model's memory (its context window) to fit your GPU automatically. /tier shows what it picked and why.

Ollama cloud

Ollama can also run large models on its own servers. Sign the Ollama app in to your free ollama.com account (setup runs ollama signin for you, or use the app's settings). The …-cloud models then appear in /model under "Ollama cloud". No API key needed.

ChatGPT plan

With a ChatGPT plan (Go, Plus or Pro) you can use your plan in qh instead of paying for an API key:

qh login chatgpt

If the Codex CLI is signed in on this computer, qh uses that sign-in. Otherwise your browser opens; sign in with ChatGPT. This goes the way the Codex CLI does (OpenCode and others do the same), which isn't OpenAI's official route for other apps, so OpenAI could change it. With Plus or Pro you can use the official route instead: qh login chatgpt-official. Then pick a model with /model chatgpt. Inside qh you can also do it from /provider → chatgpt. Usage counts against your plan's allowance; you can cap how much qh may use in ChatGPT's settings. Sign out with qh logout chatgpt.

Switching models

/model opens a list of every model you can use, grouped by where it runs. Type to search and press Enter. Each tab can use a different model; /model default <name> sets the one new tabs start with.

Modes and approvals

Press Shift+Tab to cycle how much the agent asks:

ModeWhat happens
askAsks before anything that changes something (the default where commands can't be sandboxed)
auto-editEdits files freely; still asks before running commands
autoRuns everything except dangerous commands (rm, sudo, git push…) and pay or delete clicks (the default where commands are sandboxed)
planRead-only: it explores and writes a plan; switch mode to let it act

When it asks, you can allow once, deny, or "always" allow that kind of command. /allow lists the rules you've added.

Sandbox

On by default, in every mode. /sandbox shows exactly what's in force.

  • Secrets ask first. Reading ~/.ssh, ~/.aws, .env files, keys (*.pem, id_rsa…), cloud and git credentials, browser profiles, or qh's own logins always asks, even in auto.
  • Writes stay in the project. The file tools write freely in the project and temp; anywhere else asks, even in auto. So do files that run code later: .git/hooks, shell rc files, .envrc, .qh/ and qh's config.
  • Commands run sandboxed. They can write only in the project, temp and package caches, and can't read secrets. Variables holding tokens and keys (*_TOKEN, *_KEY, passwords in URLs) are withheld from them.
  • The network goes through an allowlist. Package registries and git hosts (crates.io, npm, PyPI, GitHub…) just work. Any other host asks you first, even in auto; "always" allows that host for the session.
  • Local servers stay per tab. A dev server the agent starts in the background can be reached from that tab's later commands (curl localhost:3000), but not from other tabs, and commands can't reach other services on your machine's localhost.
  • Blocked by mistake? The agent can ask to rerun one command outside the sandbox. You're asked every time.
SystemHow commands are confined
LinuxLandlock (kernel 5.13+) and seccomp, plus private network and mount namespaces where the kernel allows them. Nothing to install.
macOSSeatbelt (sandbox-exec), built in.
WindowsRun qh sandbox setup once (it asks for admin): commands then run as hidden sandbox users with write-restricted tokens on their own desktop, and firewall filters send them only through qh's allowlist. qh sandbox remove undoes it all. Until then commands run with your access; the secret and write guards and the withheld variables still apply. Sandboxed commands can't write to other drives either. Tools that use Windows' own TLS (curl.exe, PowerShell's web commands, winget) can't make HTTPS connections inside; git, cargo, Python, Node and npm can, and dotnet restore gets packages through qh's own NuGet mirror.
Where the system can't sandbox commands (an old Linux kernel, say), /sandbox says so. The secret and write guards still apply.

Several agents at once

Each tab is its own agent with its own model and folder. They can work in parallel and talk to each other: one tab can ask another a question, hand it a job, or start a helper. Give a tab a job with /role (for example "tests"), and others send related work to it. Ctrl+G shows up to four tabs side by side; Ctrl+B shows the live map.

Undo and diff

qh keeps a copy of every file before the agent changes it. /diff shows everything the agent changed this session; /undo puts the last change back.

Team mode

Work on one project with friends. Each person runs qh on their own computer; you see who's online, what their agents are doing, read their sessions, and send messages into them. There's no server and no sign-up: qh uses the project's GitHub repo as a shared notice board, and everyone who can push to the repo is on the team.

You need: a free GitHub account each, git, and a GitHub login on your computer (install the GitHub CLI and run gh auth login).

Start a team

  1. You, in the project folder: type /team create in qh (or qh team create in a terminal). Answer two questions: who can see the code (private or public), and your friends' GitHub usernames. Check the summary and say yes. qh puts the folder on GitHub if it isn't there, keeps secret files like .env out, and invites your friends.
  2. Send your friend the line qh prints, for example qh join you/webshop.
  3. Your friend runs it. qh accepts the GitHub invite, downloads the project, and turns team mode on. Then cd webshop and qh.

From then on, just run qh in the project: team mode comes back on by itself. If the project is already on GitHub and your friends already have access, each of you just types /team on once.

Change who can see the code any time with /team private or /team public.

See and message teammates

The status bar shows who's online, like you · alex ● · sam ○ 2h ago. Notes appear when someone joins or leaves.

Type /team for a list of everyone's sessions. Pick one to:

  • read it: its recent conversation, read-only;
  • write into it: your message goes to that session on their computer.

Or type directly: /team open alex api and /team send alex api add rate limiting to login.

When a teammate (or their agent, with tell_team) asks one of your sessions to do something, it lands in the Requests tab of the team room (Ctrl+T), never straight in the session, whatever their role and whatever mode the session runs in, auto included. The status bar says · 1 request (Ctrl+T) and you get a notification. Pick it and press Enter or a to accept (it goes into that session as [accepted request from alex]: …), r to reply without starting anything (the request keeps waiting), or d to decline (alex is told privately). Questions their agents ask yours are still answered on their own from a read-only copy, unless /answers ask, which puts them in Requests too.

How you're connected

Teammates who are both online talk over an encrypted direct line: on the same network if they can, otherwise straight across the internet, and through a relay only when neither works. A strict router on one side still gets a direct line. Where UDP is blocked (some offices and campuses), qh reaches the relay over TCP on port 443, which looks like ordinary HTTPS. /team link shows, for each teammate, which path is in use, the round trip, and why a better one didn't work.

Chat, private messages and groups

The room's Chat tab lists channels on the left: # team for everyone, @login for a private conversation with each teammate, and your groups. Pick one and press Enter to write; p on the map writes privately to the person you picked. From the prompt: /dm alex the staging password changed, and /team group backend alex sam to make a group (/team group lists yours).

Write @alex in any message to ping alex (a notification, the line highlighted, and an @ on the channel's unread count); @team pings everyone. An email address like me@alex.dev doesn't ping anyone.

Chat is for people: nothing in it ever reaches an agent unless you paste it into a session yourself.

Notifications (requests, pings, private messages, a teammate's answer) follow the notify setting and show only while the terminal isn't focused; notify = "off" silences them.

Each of you works in your own clone: there's no shared folder, and nothing you write reaches a teammate by itself. While you're both online, their agent can read a file from your working copy over the encrypted direct line (read_team_file), uncommitted changes included, and see which files you've changed (list_team_files). It's read-only, answered in seconds without asking you, and every read shows in your team Activity, like alex's agent read server.js. To hand over finished work, the agent commits it to a branch qh/<login>/<topic>, pushes it (you're asked first) and tells the teammate the branch name.

Privacy and safety

  • Only people with push access to the repo can take part. Someone who just knows the repo's name gets nothing.
  • Everything qh shares (sessions, conversations, messages, file names) is encrypted with a key only the team has, so even on a public repo outsiders see noise. They can see team members' GitHub usernames and when each was last online.
  • Private messages and group chats get a second lock inside that one: a private message is sealed with a key only its two people share (from their own member keys), and a group has its own key that only its members are given. Other teammates see only sealed boxes. Both travel through the repo like everything else, so a private message reaches someone who's offline when they're back.
  • A new member gets the key from a teammate who's already in, the next time that teammate is online.
  • Each agent runs on its owner's computer, with the owner's model and keys. A teammate's message never runs without the owner allowing it, and the owner approves every file change and command it leads to.
  • A teammate's agent can read only plain files inside the project, and only while you're online: never secret files (.env, keys, anything under ~/.ssh), git's own files, or anything your .gitignore leaves out. Links pointing out of the project are refused, replies stop at 2,000 lines or 200 KB, and people you have as view only or removed get nothing. team_share_files = "off" in your config turns it off.
  • /team off stops sharing; your teammates see you go offline.
Team mode needs the project on GitHub today. GitLab and Gitea support is planned.

Project instructions

Put a QH.md file in your project with anything the agent should always know or follow ("use pytest", "never touch the migrations folder"). qh also reads AGENTS.md or CLAUDE.md if there's no QH.md. Instructions for every project go in QH.md in the config folder.

Your own commands

A markdown file becomes a command: .qh/commands/review.md in your project gives you /review. Its text is sent as your message; $ARGUMENTS in it is replaced by whatever you type after the command. Commands for every project go in commands/ in the config folder. /commands lists them.

# .qh/commands/review.md
Review the changes in $ARGUMENTS for bugs and missing tests. Be brief.

Skills

A skill is a set of instructions the agent loads only when a task needs it, so it doesn't cost context the rest of the time. Make a folder .qh/skills/<name>/ with a SKILL.md:

---
name: release
description: How to cut a release of this project
---
1. Bump the version in Cargo.toml
2. Run the tests …

Hooks

Hooks run your own shell commands when the agent does something. Add them to config.toml:

# format after every edit
[[hooks]]
event = "post_tool"
match = "write_file|edit_file"
cmd = "cargo fmt"

# block a command: exit code 2 stops it, and the message goes to the agent
[[hooks]]
event = "pre_tool"
match = "bash"
cmd = "grep -q 'rm -rf' && { echo 'not allowed' >&2; exit 2; }; exit 0"
EventWhenExit code 2
pre_toolBefore a tool runsBlocks it
post_toolAfter a tool runs; its output is added to the resultSame as success
stopWhen the agent wants to finishSends the message back so it keeps working (for example, tests still failing)

The event arrives as JSON on the command's input. match is a pattern for the tool's name; leave it out to match every tool.

MCP servers

Connect any MCP server and its tools become available to the agent:

[mcp.github]
cmd = "npx"
args = ["-y", "@modelcontextprotocol/server-github"]
env = { GITHUB_PERSONAL_ACCESS_TOKEN = "..." }
trusted = false   # true: run its tools without asking

Tools appear as github__<tool>. /mcp shows each server and how many tools it has.

Config reference

The config file is config.toml in:

  • Windows: %APPDATA%\qh\
  • Linux and macOS: ~/.config/qh/

qh setup writes it for you; edit it for anything else.

Troubleshooting

You seeDo this
"Ollama isn't answering"Start the Ollama app (or ollama serve), or pick a cloud model with /model
"rejected the API key"/provider → pick it → add a new key
"out of credit"Top up with that provider, or switch to a free or local model
ChatGPT "allowance used up"Raise qh's cap in ChatGPT settings, wait for the reset, or switch model
"isn't on GitHub yet"/team create puts the project on GitHub
"no GitHub login found"Install the GitHub CLI and run gh auth login
A teammate is online but messages are slow/team link shows how they're reached; "over relay" or "over tcp" means no direct path, usually a strict or UDP-blocking network
"waiting to be let in"A teammate who's already in needs to run qh once
Slow, or forgets thingsYour GPU fits a small context; /tier explains. A cloud model avoids the limit

Something else? Open an issue on GitHub.
